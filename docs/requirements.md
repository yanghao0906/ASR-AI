## 1. 项目概述

### 1.1 背景与目标

做一个类似小爱音箱的**最简可用**语音助手：

- **完全离线运行**，不接入任何大模型语义解析服务；
- 用户对网页说话，系统将语音识别为文字后，匹配到用户预先配置的指令并**执行对应的动作**（一期为 HTTP 操作，如调用智能家居接口；动作执行层为可扩展的 Handler 架构）；
- **相似说法归一**：'打开空调'、'开空调'、'空调开启'等不同说法命中同一条指令；
- **参数指令严格区分**：'温度调到 26 度'、'温度高一点'、'温度调低'是三种不同语义，各自提取参数、互不误命中。

### 1.2 产品定义（一句话）

> 浏览器喊话 → 后端离线识别 → 规则+相似度匹配指令 → 执行用户配置的动作（一期为 HTTP，由 ActionHandler 工厂分发）→ 网页展示结果。

### 1.3 设计原则

1. **离线优先**：ASR、匹配模型全部本地推理，无网络依赖（HTTP 动作本身除外）。
2. **无大模型**：语义理解 = 规则槽位匹配 + 中文句向量相似度，两者职责严格分离。
3. **规则优先于相似度**：凡带参数的指令必须走规则，相似度只用于无参数的开/关类指令（防止"高一点"与"调低"这类字面相近、语义相反的说法被误归一）。
4. **配置文件是唯一事实源**：指令、说法、规则、动作、系统参数全部以 YAML 文件为准，前端管理页的修改最终写回该文件。
5. **一期做薄**：唤醒词、TTS、连续会话等全部后移到演进路线，架构上预留位置。

- 语音唤醒词（含 KWS 常驻监听）

- 用户登录鉴权
- 档位类参数（"最大/最小/自动"）、拼音级容错
- 指令的"设备 × 动作"自动组合建模

## 3. 总体架构

### 3.1 链路图

```
┌────────────────────────── 浏览器（Vite 前端） ──────────────────────────┐
│  麦克风按钮 → getUserMedia 采音 → 前端静音检测自动停 → 编码 WAV 上传      │
│  展示：识别文本 / 命中指令 / 置信度 / 执行结果 / 候选列表 / 历史记录      │
└───────────────────────────────┬──────────────────────────────────────┘
                        POST /api/voice/command (audio/wav)
                                ▼
┌────────────────────────── Java 后端（常驻） ───────────────────────────┐
│  ① WAV 解码（16kHz 单声道 PCM）                                        │
│  ② 离线 ASR（Vosk + vosk-model-cn-0.22 中文模型）→ 文本                │
│  ③ 文本归一化（去标点/语气词、中文数字→阿拉伯数字）                      │
│  ④ 意图匹配引擎                                                        │
│     ├ 第一级：规则槽位（各指令的 regex，配置顺序=优先级）                │
│     └ 第二级：句向量相似度（DJL+ONNX bge-small-zh，仅无参数指令）       │
│  ⑤ 动作执行器（ActionHandler 工厂按 type 分发，一期内置 HTTP Handler）│
│  ⑥ 配置管理（commands/actions/settings YAML 读写 + 热加载） / 日志      │
└───────────────────────────────┬──────────────────────────────────────┘
                                ▼
                     用户配置的目标系统（智能家居网关等）
```

后端空闲时无任何监听任务，CPU 占用约等于 0；模型（ASR + 句向量）启动时加载、常驻内存。

### 3.2 关键技术决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 前端直接采集 16kHz PCM 并编码 WAV 上传，不用 MediaRecorder(webm/opus) | 避免 Java 侧引入 opus/ffmpeg 解码依赖，`javax.sound.sampled` 原生读 WAV |
| D2 | 两级匹配：规则槽位优先，相似度只兜底无参数指令 | 满足"归一"与"严格区分"并存的核心诉求（见 1.3 原则 3） |
| D3 | 配置文件为唯一事实源，前端管理页修改由后端写回文件 | 一期不做数据库，保持简单；热加载让改动即时生效 |
| D4 | 一体化接口 `/api/voice/command` + 独立文本匹配接口 `/api/match/text` | 前者主流程一次调用；后者服务测试面板，免语音调试匹配引擎 |
| D5 | 后端托管前端构建产物，单进程部署 | 一个 jar + 一个配置文件 + 模型目录即可运行，符合跨平台目标 |
| D6 | 动作执行层采用工厂模式：`ActionHandler` 接口 + 工厂按 `actions[].type` 分发 | 新增动作类型（本地命令、模拟按键等）只需新增 Handler 实现类，匹配引擎、接口协议零改动 |
| D7 | 动作配置从指令中抽离（独立 `actions.yaml`，指令以动作 id 引用）；`type` 之后的字段由 Handler 自定义并自行校验 | 动作可复用；指令管"听懂"、动作管"执行"；引擎对动作字段结构零假设（不透明透传） |
| D8 | ASR 引擎由 sherpa-onnx + SenseVoice-small 切换为 Vosk（`com.alphacephei:vosk`，Maven Central 直接依赖，JNA 绑定）+ vosk-model-cn-0.22 | 依赖管理简单（无需私服托管 jar）；官方提供 linux x86_64/aarch64/armv7l/riscv64 native，国产化迁移成本低；大模型实测 10/10、同音错字 0 例。代价：无 ITN（数字保持中文，FR-3 归一化必做）、模型约 2GB 且加载约 22s（常驻服务可接受）。SenseVoice 保留为备选（ITN、更小更快，见 poc-report 对照数据） |

### 3.3 重要环境约束（必须写进部署说明）

浏览器的 `getUserMedia`（麦克风）**仅在安全上下文可用**：`localhost` 或 HTTPS。局域网内用 `http://192.168.x.x` 访问时浏览器会禁用麦克风。可选解法：

- 本机使用：直接访问 `localhost`（默认推荐，零配置）；
- 局域网多设备使用：后端配置自签证书启用 HTTPS（部署文档给出脚本）。

## 4. 功能需求

> 编号规则：FR-xx。每条含验收标准，作为一期验收依据。

### FR-1 语音输入（前端）

- 页面提供麦克风按钮，**点击开始录音**，录音中显示音量指示与"停止"按钮；
- 前端静音检测：连续静音约 1 秒（可配，默认 1000ms）**自动结束录音**并立即上传识别；
- 手动点击"停止"随时可结束（兜底）；
- 最长录音 60 秒强制结束；
- 采集规格：16kHz、16bit、单声道，前端编码为 WAV 上传；
- 浏览器授权被拒/无麦克风时给出明确提示。

**验收**：点击后说话，停顿约 1 秒自动上传；点击停止立即上传；授权拒绝时有友好错误提示。

### FR-2 指令一体化接口（后端）

- `POST /api/voice/command`，请求体为 WAV 音频；
- 一次调用完成：ASR → 归一化 → 匹配 → 执行动作（经 ActionHandler 工厂分发）→ 返回完整链路结果；
- 响应字段：

```json
{
  "asr_text": "空调温度调到二十六度",
  "normalized_text": "空调温度调到26度",
  "match": {
    "command_id": "ac_temp",
    "name": "空调温度调节",
    "by": "rule | similarity",
    "score": 0.83,
    "slots": { "value": "26", "mode": "set" }
  },
  "candidates": [ { "command_id": "ac_on", "name": "打开空调", "score": 0.71 } ],
  "action": { "ok": true, "action_id": "ha_climate_set_temp", "handler": "http", "status": 200, "elapsed_ms": 120, "summary": "{...响应摘要...}" },
  "elapsed_ms": 890
}
```

- `match` 为 null 表示未命中（此时 `candidates` 返回 Top3 供前端展示）；
- 动作执行失败不掩盖识别结果：失败信息完整带回前端。

**验收**：一条 3 秒语音从上传到收到完整响应，端到端 < 2 秒（普通 PC）。

### FR-3 文本归一化（后端）

匹配前统一处理，顺序执行：

1. 去首尾空白与标点；
2. 全角转半角；
3. 去句尾语气词（啊、呀、哦、呢、吧、嘛）；
4. 中文数字转阿拉伯数字，支持一～一百（例："二十六"→26、"一百零五"→105）——**必做**：Vosk 无 ITN，ASR 输出数字保持中文（PoC 实测），此步是数字指令可用的前提；
5. 多余空白压缩。

**验收**："开空调啊。"归一化为"开空调"；"温度调到二十六度"含"26"。

### FR-4 意图匹配引擎（后端，核心）

两级流水线：

**第一级：规则槽位匹配（优先）**

- 按指令在配置文件中的顺序（即优先级）逐条尝试其 `patterns` 正则；
- 命中即停止，通过命名捕获组与固定 `slots` 映射提取参数；
- 典型参数：`value`（数字）、`mode`（set/up/down）、`step`（幅度，默认 1）；
- 同一指令可配多条规则区分语义方向（见附录 A 示例）。

**第二级：句向量相似度匹配（兜底）**

- 仅对**未配置 `patterns` 或未被规则命中**的无参数指令生效；
- 启动/热加载时预计算每条指令所有 `phrases` 的向量；
- 运行时计算用户文本向量，与各短语求余弦相似度，指令得分 = 其短语最高分；
- 全局最高分 ≥ 阈值（默认 0.75，可配）则命中；
- 未达阈值视为未命中，返回 Top3 候选。

**启动校验（配置加载时）**

- 只配了 `phrases` 而其引用动作中的 `${槽位}` 占位符需要参数 → 报错拒绝加载；
- `patterns` 正则语法错误 → 报错并指出行号；
- 指令 id / 动作 id 重复 → 报错；
- 指令引用的动作 id 不存在、动作 `type` 无对应已注册 Handler → 报错（详见 FR-6）。

**验收（对应用户原始诉求）**：
- "打开空调 / 开空调 / 空调开启 / 帮我把空调打开" → 均命中 `ac_on`（相似度路径）；
- "温度调到 26 度" → `value=26, mode=set`；
- "温度高一点 / 调高一点" → `mode=up, step=1`；
- "温度调低" → `mode=down, step=1`；
- 以上参数指令之间**零互相误命中**；"打开空调"与"关闭空调"不互相命中。

### FR-5 未命中与候选执行（前端）

- 未命中时展示：识别文本 + "未命中提示" + Top3 候选（指令名 + 相似度得分）；
- 每个候选带"执行"按钮，点击后直接执行该指令的动作（不再识别）；
- 候选区同时是阈值调参的观察窗口。

**验收**：说一句未配置的话，出现候选；点击候选执行后结果与直接语音命中一致。

### FR-6 动作执行器（后端，工厂模式 ActionHandler）

**架构**：

```
ActionHandler（接口）—— 动作配置结构由各 Handler 自治
 ├─ String type()                          // 动作类型标识，对应 actions[].type
 ├─ ValidationResult validate(ActionDef)  // 校验本类型自有字段（如 url 合法性）
 └─ ActionResult execute(ActionDef, slots, ctx)

ActionHandlerFactory
 └─ type → Handler 注册表；Spring 容器自动收集所有实现类完成注册
```

- 动作定义独立存放于 `config/actions.yaml`，指令以 `action: <动作id>` 引用（见第 5 节），同一动作可被多条指令复用；
- **`type` 之后的动作字段完全由对应 Handler 自行定义、解析、校验与执行**，引擎不做任何结构假设，作为不透明配置整体透传；
- 平台级约定仅两条，对所有 Handler 生效：
  1. `type` 分发：工厂按动作定义的 type 路由到 Handler；
  2. `${槽位名}` 占位符：引擎在分发前对动作配置做通用递归字符串替换，Handler 拿到已替换配置 + 原始 slots（Handler 也可不用占位符，直接读取 slots 自行组装）；
- **一期唯一内置实现：`HttpActionHandler`（type = http）**，自有字段与行为：
  - 字段：`method` / `url` / `headers` / `body`，占位符可出现在任意字段任意位置；
  - 默认超时 10 秒（可配），超时或连接失败返回明确错误，**不自动重试**；
  - 响应体只保留摘要（前 500 字符）用于前端展示与日志；
- 配置校验（FR-4 启动校验项）：
  - 动作 `type` 未注册 → 报错并指出动作 id；
  - 指令引用的动作 id 不存在 → 报错并指出指令 id；
  - 动作占位符 `${xxx}` 未被引用它的任何指令 patterns 提供 → 报错（引擎级通用检查，不感知字段结构，仅扫描字符串）；
- **扩展约定**：新增动作类型 = 新增一个 Handler 实现类（如二期 `local_command`、`keystroke`），引擎、工厂、接口协议零改动；前端动作编辑器按 type 动态渲染该 Handler 的自有字段表单。

**验收**：
- 温度指令的 26 成功替换进请求体发出（可用 httpbin 类服务验证）；
- 同一动作被两条指令引用，均能正确执行；
- 配置 `type: xxx`（未注册）报错并指出动作 id；指令引用不存在的动作 id 报错并指出指令 id；
- 追加一个仅打日志的 `log` Handler（不发布到前端下拉，供调试与扩展性验证），引擎不解析其字段结构、不改引擎代码即可被 `type: log` 调用。

### FR-7 指令与动作配置管理（前端 + 后端）

- 前端两个管理页：
  - **指令管理**：列表（启用状态、短语数、规则数、引用动作）、新增、编辑、删除、启用/停用；编辑项：基础信息（id、名称）、动作引用（下拉选择已有动作）、示例说法（多条，可增删）、参数规则（正则 + 槽位映射）；
  - **动作管理**：列表（id、类型）、新增、编辑、删除；编辑项：基础信息（id、名称）、动作类型下拉选择（一期仅 http）+ 按 `type` 动态渲染该 Handler 的自有字段表单（http：method/url/headers/body，带模板变量插入按钮）；
- 删除动作前检查引用：仍被指令引用则拒绝并提示引用方；
- 后端提供指令与动作两组 CRUD 接口，**每次修改分别写回对应 YAML 并触发热加载**；
- 同时保留直接手改文件的能力：文件监听（轮询 mtime 即可）发现变化 ≤3 秒热加载；
- 加载失败（校验不通过）时：保留上一份有效配置继续运行，前端全局告警显示错误详情。

**验收**：前端新增一条引用已有动作的指令后 ≤3 秒内语音即可命中；动作删除的引用保护生效；手改文件同样生效；写坏正则时系统不崩且告警。

### FR-8 匹配测试面板（前端）

- 输入框输入任意文本（如"开一下空调"），点击测试；
- 调用 `POST /api/match/text`（只匹配不执行）；
- 展示：归一化后文本、命中结果（指令、路径 rule/similarity、得分、槽位）、未命中时的 Top3 候选得分列表。

**验收**：调阈值过程中全程无需对麦克风说话。

### FR-9 执行历史（前端 + 后端）

- 后端内存环形队列保留最近 200 条 + 追加写入日志文件（`logs/`，按天滚动）；
- 每条记录：时间、耗时、ASR 原文、归一化文本、命中指令（或未命中）、匹配路径与得分、槽位、动作执行结果；
- 前端历史页倒序展示，支持按命中/未命中筛选。

**验收**：每次语音调用后历史页立即可见该记录。

### FR-10 系统设置（前端 + 后端）

可视化调整并写回配置文件：

- 相似度阈值（0.5～0.95，滑杆，附"当前未命中率"参考）；
- 前端静音停止时长（500～3000ms）；
- HTTP 超时（http Handler 专属参数，3～30s）；
- 模型信息只读展示（名称、版本、内存占用）。

**验收**：修改阈值后立即生效于下一次匹配。

## 5. 配置文件设计

文件：`config/commands.yaml`（指令）+ `config/actions.yaml`（动作）+ `config/settings.yaml`（系统参数）。**指令与动作解耦**：指令只描述"怎么听懂"，动作只描述"怎么执行"，指令通过动作 id 引用，同一动作可复用。

```yaml
# config/settings.yaml
settings:
  match:
    similarity_threshold: 0.75
  audio:
    silence_ms: 1000          # 前端静音自动停时长（接口下发给前端）
  action:
    http_timeout_ms: 10000    # http Handler 专属参数
```

```yaml
# config/actions.yaml —— 动作定义；type 之后的字段由对应 Handler 自定义
actions:
  - id: ha_climate_on                     # 动作唯一 id，供指令引用
    name: 打开空调                         # 展示名（可选）
    type: http                            # 动作类型 → 工厂分发到 HttpActionHandler
    method: POST                          # ↓ 以下均为 http Handler 的自有字段
    url: http://192.168.1.10:8123/api/services/climate/turn_on
    headers:
      Authorization: "Bearer xxx"
    body: '{"entity_id": "climate.ac"}'

  - id: ha_climate_set_temp
    name: 设置空调温度
    type: http
    method: POST
    url: http://192.168.1.10:8123/api/services/climate/set_temperature
    body: '{"entity_id":"climate.ac","temperature":"${value}","mode":"${mode}","step":"${step}"}'
```

```yaml
# config/commands.yaml —— 指令定义，动作以 id 引用
commands:
  - id: ac_on                          # 唯一 id
    name: 打开空调                      # 展示名
    enabled: true
    action: ha_climate_on               # 引用 actions.yaml 中的动作 id
    phrases:                           # 相似说法示例（向量匹配用，无参数指令）
      - 打开空调
      - 开空调
      - 空调开启
      - 帮我把空调打开

  - id: ac_temp                        # 参数类指令：必须且只能走 patterns
    name: 空调温度调节
    enabled: true
    action: ha_climate_set_temp
    patterns:
      - regex: '温度.*?(设|调)到?(?P<value>\d+)\s*度'
        slots: { mode: set }
      - regex: '(调高|升高|高一点|太?冷)'
        slots: { mode: up, step: 1 }
      - regex: '(调低|降低|低一点|太?热)'
        slots: { mode: down, step: 1 }
```

指令字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，稳定标识 |
| `name` | 是 | 展示名 |
| `enabled` | 否 | 默认 true，停用后不参与匹配 |
| `action` | 是 | 引用的动作 id（定义在 actions.yaml） |
| `phrases` | 无参数指令必填 | 相似度匹配的示例说法，建议 ≥3 条且覆盖不同语序 |
| `patterns` | 参数指令必填 | 规则列表，按序匹配；`regex` 支持命名捕获组，`slots` 为固定键值 |

动作字段说明：

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 动作唯一 id，被指令引用；删除前须无指令引用 |
| `name` | 否 | 展示名 |
| `type` | 是 | 动作类型，工厂据此分发到对应 ActionHandler；一期仅 `http` |
| （其余字段） | 由 Handler 决定 | `type` 之后完全由 Handler 自行定义与校验，引擎不解析、透传执行；`${槽位名}` 占位符为平台级通用约定 |

约束（加载时校验，见 FR-4）：`phrases` 与 `patterns` 至少其一；指令引用的动作 id 必须存在；动作中的 `${槽位}` 占位符必须能被所有引用它的指令 patterns 提供。

## 9. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| Vosk 大模型资源占用（模型约 2GB、加载约 22s） | 中 | 常驻服务启动一次加载可接受；实测常驻内存见 poc-report；资源受限场景可降级 vosk-model-small-cn-0.22（44MB，精度 8/10）；备选方案 SenseVoice（228MB）保留 |
| 相似度误判（反义/相近指令） | 中 | 硬约束"参数指令只走规则" + 阈值可调 + 候选确认交互 + 测试面板观察（PoC 实测反义对交叉分 0.75~0.80，阈值建议初值 0.80） |
| Windows 上 ONNX Runtime 官方包 DLL 初始化失败（句向量侧） | 低 | 已验证解法：`onnxruntime.native.path` 挂载可用 DLL（PoC 已实现）；详见 poc-report §3.1 |
| ASR 同音错字导致匹配失败 | 低 | 大模型实测同音错字 0 例（10/10）；错字句规则不命中时走 Top3 候选兜底；二期拼音级模糊匹配 |
| HTTP 目标不可达/超时 | 低 | 明确超时与错误提示，不自动重试（目标系统幂等性未知） |
| 浏览器麦克风安全上下文限制 | 低 | localhost 默认可用；局域网部署给自签 HTTPS 方案（见 3.3） |
| 中文数字口语变体识别偏差 | 中 | FR-3 归一化（必做）覆盖一～一百常见说法，超出范围走候选确认 |

## 10. 演进路线

**二期候选（按优先级）**

1. 会话窗口：点击一次后保持 N 秒连续多指令（"打开空调…温度 26 度…风速自动"），超时或"退出"结束（一期架构已预留状态机）。
2. 语音唤醒词：方案 A 后端直连麦克风 + KWS 常驻（Vosk 无 KWS 能力，届时需引入 sherpa-onnx KWS 组件，忠实音箱形态，需麦克风在主机）；方案 B 浏览器页面常开 + 前端唤醒检测。届时按部署形态决策。
3. TTS 播报：离线中文 TTS（Vosk 无 TTS 能力，届时评估 sherpa-onnx TTS 等组件）："好的，温度调到 26 度"。
4. 拼音级容错匹配、档位槽位（最大/最小/自动）。

**三期方向**

- 嵌入式部署（树莓派等，后端直连麦克风阵列）；
- 录音自定义唤醒词本地训练；
- 指令"设备 × 动作"组合建模；
- 动作类型扩展：新增 ActionHandler 实现（本地命令/脚本、模拟按键、系统操作），配置改 `type` 即用，引擎零改动。
