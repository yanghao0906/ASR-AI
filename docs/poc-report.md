## 1. 验证目标与方法

按需求文档第 8 节的技术选型，在 **Java 后端**（非 Python）完整跑通核心推理链路，验证的两个可交付组件与正式工程同构：

- **ASR**：sherpa-onnx 1.13.8 Java API + SenseVoice-small（int8，228MB），输入 16kHz/16bit/单声道 WAV；
- **句向量**：DJL 0.38.0 + ONNX Runtime + bge-small-zh-v1.5（ONNX fp32，90MB，CLS 向量 + L2 归一化 + 余弦相似度）。

测试音频用 Windows SAPI（Microsoft Huihui，zh-CN）合成 **10 条** 16k WAV，覆盖需求文档附录 A 的全部场景：4 条 `ac_on` 同义说法、`关闭空调`（反义）、3 条温度参数指令、1 条无关句、1 条跨设备语句（开灯）。

环境：Windows 11 x64 / JDK 17.0.14 / Maven 3.8.4 / 纯 CPU 推理 / 模型与推理全程本地（离线）。

> **v1.1 增补（2026-09-15）**：基于 sherpa-onnx 集成复杂度（jar 不在 Maven Central 需私服托管、多平台迁移面大）与国产化迁移考量，ASR 引擎切换为 **Vosk**（小/大双模型实测见 §5，国产化评估见 §6）。下文 §2 的 sherpa 数据保留作为备选方案与对照。两套方案共用同一批测试音频与同一套句向量匹配链路，结果可直接对比。

## 2. 验证结果（sherpa-onnx 方案，现为备选）

### 2.1 ASR（sherpa-onnx + SenseVoice-small）

- **10/10 全部识别正确**；模型加载 2.2s；
- 单条解码 103~240ms，**最大 RTF 0.099**（验收线 0.3）；
- **ITN 自动生效**："空调温度设置到二十六度" → "空调温度设置到26度"（FR-3 数字归一化的最大头已由模型侧解决）；
- 输出自带标点（"。""？"）；Java API `getResult().getText()` **未泄漏** `<|zh|>` 等控制标签（仍建议保留防御性剥离）。

### 2.2 句向量匹配（DJL + ONNX Runtime + bge-small-zh）

- 模型加载 325ms，首次推理（含 ORT 会话初始化）50ms，**稳态单条编码 ≤10ms**（验收线 100ms）；
- 指令得分（阈值 0.75，指令得分 = 其短语最高分）：

| 查询（ASR 实际输出） | ac_on | ac_off | light_on | 结果 |
|---|---|---|---|---|
| 打开空调 / 开空调 / 空调开启 / 帮我把空调打开 | **1.000** | 0.76~0.80 | 0.51~0.59 | 全部命中 ac_on ✔ |
| 关闭空调 | 0.748 | **1.000** | 0.467 | 命中 ac_off，不串 ac_on ✔ |
| 今天天气怎么样 | 0.346 | 0.377 | 0.292 | 全部远低于阈值 → Top3 候选 ✔ |
| 把客厅的灯打开 | 0.573 | 0.517 | **0.989** | 命中 light_on ✔（跨设备区分良好） |
| 空调温度设置到26度 / 高一点 / 调低 | ≤0.714 | ≤0.714 | ≤0.417 | 均低于阈值，参数指令走规则 ✔ |

- **参数指令交叉演示**（设计原则 3 的实证依据）："空调温度高一点" 对 temp_up=0.876 / temp_down=0.793，"空调温度调低" 对 temp_up=0.801 / temp_down=0.917 —— **两个方向的分差仅 0.08~0.12**，靠相似度无法保证"高一点/调低"严格区分，**参数指令必须走规则** 的文档结论成立。
- bge 检索前缀（"为这个句子生成表示以用于检索相关文章："）在本场景下使得分整体下降且区分度变差，**指令匹配场景不应添加**。

### 2.3 验收对照（PMA 建议的 PoC 验收标准）

| 项 | 标准 | 实测 | 结论 |
|---|---|---|---|
| 功能正确 | WAV→正确文本、ITN 数字、无标签残留 | 10/10，"26" 正确 | ✅ |
| ASR 延迟 | 5s 语音 <1s（RTF<0.3） | RTF≤0.099 | ✅ |
| 句向量延迟 | 单条 <100ms | ≤10ms | ✅ |
| 同义 Top1 命中率 | ≥95%（阈值 0.75） | 6/6 = 100% | ✅ |
| 反义零互串 | 交叉得分 <0.6 | 0.75~0.80（未达绝对值），但 Top1 零互串 | ⚠️ 见 4.3 |
| 离线运行 | 断网全流程可用 | 全本地，无任何网络调用 | ✅ |
| 资源 | 两模型常驻 <1.5GB | 模型文件合计 320MB，粗估 RSS <1GB（未精确测量） | ✅ |
| 平台 | Windows x64 native | Windows 11 验证通过；Linux 未测 | ✅/— |

## 3. 关键发现（影响正式工程）

### 3.1 【重要】ONNX Runtime 官方包 DLL 初始化失败与解法（与 ASR 引擎无关）

同一 JVM 中同时加载两套 ONNX Runtime 是本 PoC 最大的坑，且**与 sherpa 无关**（隔离实验证明官方包单独加载即失败；该问题影响的是句向量侧，**Vosk 方案同样受影响并沿用同一解法**）：

- `com.microsoft.onnxruntime:onnxruntime` 官方包的 win-x64 核心 `onnxruntime.dll`（1.21.1 / 1.28.0 均试）在本机 `System.load` 阶段报 **Win32 错误 1114（DLL 初始化例程失败）**；VC++ 运行库 14.50 正常，原因未深究；
- sherpa-onnx native 包自带的 `onnxruntime.dll`（1.28.2）**本机验证可用**；
- **已验证的解法**：将 sherpa 的核心 DLL 与官方包的 `onnxruntime4j_jni.dll` 置于同一目录，设置系统属性 **`onnxruntime.native.path`** 指向该目录；两者 ORT C API 版本同为 28，二进制兼容。两种加载顺序（先 sherpa / 先 DJL）均通过。实现见 `VoskMain#prepareOrtNativeDir`（与 `PocMain` 同款）；
- **生产建议**：Spring Boot 启动早期执行同样的提取与属性设置；或将官方 ORT 依赖 exclusion 后统一由 sherpa 的 native 包供给核心 DLL（若彻底去 sherpa 化，需把这份验证可用的 `onnxruntime.dll` 作为独立资产随包分发）。此约束应写入部署说明。

### 3.2 sherpa-onnx 的依赖分发

- 官方**不发布 Maven Central**（仅 GitHub Release 的 `sherpa-onnx-jvm-*.jar` + 平台 native jar）；GitHub 直连不可用时可经 gh-proxy / SourceForge 镜像（`poc/setup_jars.sh`）；
- 正式工程需以 **内部 Nexus/私服** 托管这两个 jar（Windows/Linux x64 各一份 native），否则部署机无法构建。**Vosk 无此问题**（`com.alphacephei:vosk` 在 Maven Central 直接依赖）——这是选型切换的主要动因之一。

### 3.3 相似度阈值策略警示

反义/相近指令对的**绝对相似度偏高**（打开 vs 关闭空调交叉分 0.75~0.80，"打开灯"对 ac_on 0.573）。阈值 0.75 时虽零互串，但安全边际只有 ~0.25，且真实用户说法（非库内原句）命中分会低于 1.0。建议：

1. 每条指令短语库建议 ≥4 条、覆盖不同语序（文档建议 ≥3，可再收紧）；
2. 上线初期用测试面板（FR-8）以真实语音样本调参，阈值建议先取 **0.80** 观察；
3. 可选增强：Top1 与 Top2 分差 < 0.05 时降级为"候选确认"而非直接执行。

### 3.4 FR-3 归一化的输入现实（按引擎分述）

- **Vosk（现行选型）**：输出无标点、空格分词小写、**无 ITN（数字保持中文"二十六"）**——FR-3 第 4 步"中文数字→阿拉伯数字"为**必做**（数字指令可用的前提）；去空格与全半角处理同样需要；
- **SenseVoice（备选）**：输出自带标点（"。""？"），FR-3 第 1 步"去标点"必须在匹配前执行；数字归一化大头已由模型 ITN 覆盖，FR-3 第 4 步作为兜底（覆盖 ITN 之外的口语变体）。

## 4. 需求分析要点（PMA 评审）

### 4.1 架构评估结论

总体自洽：单 jar 单进程、指令/动作解耦 + Handler 自治字段 + 工厂 Spring 自动注册的边界干净，"新增动作类型零改引擎"成立。需补齐的文档问题：

1. **示例正则是 Python 语法**：`(?P<value>\d+)` 在 Java 需写作 `(?<value>\d+)`，照文档实现会启动报错（建议 v1.3 修正）；
2. **热加载双触发竞态**：前端写回触发热加载 + 文件 mtime 轮询触发并存，需去抖或版本号去重；
3. **并发未定义**：ASR/ONNX 推理是否可并行、多请求排队策略，直接影响 <2s 指标与内存规划；
4. **异常分支缺失**：ASR 空文本/纯噪声的行为、match 成功但 action 失败的 HTTP 状态码、非法 WAV 校验未约定；
5. **执行与热加载竞态**：候选一键执行瞬间配置被删/停用以哪份为准；
6. SenseVoice 标签：实测 Java API 不泄漏，FR-3 保留防御性剥离即可。

### 4.2 待需求方确认（按影响排序）

1. 并发策略：一体化接口串行排队还是并行推理？
2. 热加载一致性语义（执行中配置变更的取舍 + 双触发去重）；
3. ASR 空结果/纯噪声的响应契约；
4. 执行历史是否需跨重启保留（当前内存队列重启即失）；
5. 无参指令引用含 `${槽位}` 动作时的校验细则。

## 5. Vosk 方案验证（v1.1 增补，现行选型）

### 5.1 集成与依赖

- `com.alphacephei:vosk:0.3.45` 直接从 **Maven Central** 引入（JNA 绑定，Java 包跨平台同一 jar）；win64 native 为官方 zip 解压即用（libvosk.dll + MinGW 运行库），设 `jna.library.path` 指向即可；
- **关键坑**：JNA 默认按平台编码（Windows=GBK）解码 native 字符串，中文识别结果会乱码，必须设置 `jna.encoding=UTF-8`；
- 模型加载：small 592ms / cn-0.22 约 22s（常驻服务一次性成本，可接受）。

### 5.2 ASR 实测（同一批 10 条音频，小模型 vs 大模型）

| 指标 | vosk-model-small-cn-0.22（44MB） | vosk-model-cn-0.22（1.3GB zip / 2.0GB 解压） | SenseVoice-small int8（对照，228MB） |
|---|---|---|---|
| 识别正确率 | **8/10** | **10/10** | 10/10 |
| 同音错字 | 2 处（"设置到"→"设知道"、"调低"→"调的"、数字后多字） | **0 处** | 0 处 |
| 数字输出 | 中文"二十六"（无 ITN） | 中文"二十六"（**无 ITN**） | ITN 自动"26" |
| 稳态 RTF | 0.06~0.16 | 0.16~0.20 | 0.05~0.10 |
| 模型加载 | 592ms | ~22s | ~2s |
| 输出形态 | 无标点、空格分词 | 同左 | 带标点 |

**结论：大模型解决了同音错字问题（8/10 → 10/10），但不解决数字问题——Vosk 全系无 ITN，"二十六"→"26" 必须由 FR-3 归一化完成**（该步从"兜底"升级为"必做"）。

### 5.3 匹配链路（大模型 ASR 输出 + bge-small-zh，与 §2.2 同一套链路）

全部关键检查 PASS：ac_on 四种说法 Top1 全命中；"关闭空调"命中 ac_off 不串 ac_on；无关句全部低于阈值；开灯语句命中 light_on；参数指令零误命中。参数指令交叉得分演示（temp_up vs temp_down 分差 0.08~0.12）与 §2.2 一致，"参数指令必须走规则"结论不变。**注**：大模型把"二十六"完整识别为中文数字后，FR-3 归一化即可得到"26"，数字指令链路闭环成立。

### 5.4 资源实测（大模型）

- Java 进程工作集（Maven JVM + 模型加载后驻留）：**约 2.8GB**（其中模型为文件映射页，内存紧张时可被系统换出；small 模型场景 < 500MB）；
- 需求非功能指标"模型常驻内存 < 1.5GB"已按实际修订为 **< 3GB，部署机内存建议 ≥ 8GB**（requirements v1.3 第 7 节）；
- 首条解码含懒加载（small 985ms / 大模型更明显），生产应在启动后做一次预热。

### 5.5 选型结论

**采用 Vosk + vosk-model-cn-0.22**：精度 10/10 追平 SenseVoice、同音错字 0 例；依赖从 Maven Central 直取（无 sherpa 的私服托管负担）；国产化迁移面小（§6）。代价与对策：无 ITN（FR-3 必做，已修订）、模型 2GB/加载 22s（常驻可接受、预热兜底）、RTF 略高但仍 5 倍余量于实时。SenseVoice 保留为备选（资源受限或需要 ITN 时切换，PoC 代码 `PocMain` 即备选方案参考实现）。

## 6. 国产化（信创）环境迁移评估

依据 vosk-api v0.3.45 与 sherpa-onnx v1.13.8 官方发布资产清单（2026-09-15 取证）：

| 目标环境 | Vosk | sherpa-onnx | 说明 |
|---|---|---|---|
| 海光/兆芯（x86_64）+ 麒麟 V10/统信 UOS | **易**：官方 linux-x86_64 包 | 易：官方 linux-x64 包 | 换 native + 改加载路径，Java 代码零改动 |
| 飞腾/鲲鹏（aarch64） | **易**：官方 linux-aarch64 包 | 易：官方 linux-aarch64 包 | 同上 |
| 龙芯 LoongArch | **难**：无官方构建，Kaldi 体系源码自编译 | 难：无官方构建 | 两者同级；句向量侧 onnxruntime 也需 Loongnix 社区构建或自编译 |
| RISC-V（SpacemiT 等） | 中：有官方 riscv64 包 | 中：有 spacemit 专用包 | 均非 NPU 优化 |
| 鸿蒙设备端 | 无 ohos 包 | 有 ohos 包 | 本项目后端为 Java 服务，部署于服务器 OS，不受影响 |

- 句向量侧（DJL + ORT）与 ASR 选型无关：官方 native 覆盖 linux x64/aarch64，信创主流平台可用；Windows 上需 §3.1 的 DLL 挂载方案；
- 两引擎及模型许可均为 Apache-2.0，信创无授权风险；
- **总体结论：信创主流平台（x86_64/aarch64）迁移难度低；龙芯需单列专项（源码自编译 + 全链路 native 适配）。**
